# WP-08 评审记录：Pi runtime adapter 与 Recovery

> 本文是实现评审材料，不是新的实现契约。WP-08 已通过用户评审；未实现最终 CLI/SDK，也未接真实 provider。

## 范围与边界

- 使用已锁定的 `@earendil-works/pi-agent-core@0.86.0` 公开 `AgentHarness`/`AgentLane`/session API，以及 `@earendil-works/pi-ai@0.86.0` 的 `Models`。没有 Pico3、私有 `ModelRuntime`、`watchSession()` 或包内 `src`/`dist` import。
- `PiArcRuntime.attach` 要求调用方执行同实例 reconciliation、Environment anchor 校验和知识快照校验；`recoverController` 提供直接绑定 WP-06 `RunController.recover` 的 composition 入口。上述检查结束前不驱动任何 open operation 或新模型请求。返回的 `open` 只是 Pi runtime inventory，不是 Action 完成 Evidence。
- `PiToolAdapter` 将 WP-07 的九个工具映射到 Pi 的公开 schema/tool 接口，固定 `toolExecution: "sequential"`。`play`（含 RESET）为 `replay: "never"`；其余只读或条件幂等工具为 `safe`，并用稳定 invocation memo 固定参数摘要。
- 首个 `play` 开始前写入脱敏的 `tool.admitted` runtime record，按 Pi `turnId` 恢复同一 assistant response 的门禁；此后所有工具调用均以 `observation_required` 拒绝。该 record 只证明准入，不证明 Environment 已接受或完成 Action。
- `controllerPlayPort` 把稳定 Pi invocation ID 作为 Run 内 Action ID；模型结果只从 controller 已提交 Turn 与已归档末帧产生。`RuntimeKnowledgeBridge` 从 Turn commit 与 GUIDE/WORKING 快照构造恢复消息，并对 RESET/checkpoint 使用冻结的 boundary 内容。
- Context Boundary 使用确定性 Pi operation ID：先持久接纳恢复 prompt，再确认 boundary，最后 `drive`。若在接纳与确认之间中断，重启时识别同一 open operation，确认后继续，不重复 RESET。
- 模型已知失败按 `model_failure` 终止；非终局停止最多一次 continuation、一次新 Context 恢复，仍无 Action 时为 `model_no_progress`。检查覆盖普通运行与恢复后的 open run；部分 provider tool call 不进入 Environment。
- runtime record 只保存 model identity、operation/invocation/turn identity、状态和错误 code，不写模型正文、工具参数、凭据或 Raw Frame。Environment 权威始终为 receipt/Turn commit。

## 评审发现与处理

1. Pi 工具循环默认并非本包所需的顺序语义：显式配置 `sequential`，并加上持久化的 same-response 门禁；仅依赖 Pi 的工具执行模式不够。
2. Pi 的 tool memo/settlement 不证明 Environment Action 完成：Action ID、receipt、Turn commit 与 Unknown Outcome 仍由 WP-06 controller 管理；runtime 只在其恢复检查之后驱动模型。
3. RESET/checkpoint boundary 若在模型看到恢复消息前确认，会提前开放 Action：改为 `accept` → `acknowledge` → `drive`，并用确定性 operation ID 处理接纳后崩溃。
4. 恢复消息若重新读取活动笔记，可能偏离已冻结 boundary：现从 prepared boundary 使用固定 GUIDE/WORKING 内容。
5. 挂起模型 operation 的 continuation 次数不能在恢复后重置：runtime 保存无进展阶段，`resumeWaiting` 沿原阶段继续。
