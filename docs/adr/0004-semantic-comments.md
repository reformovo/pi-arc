# 用语义注释保存代码中不可见的设计意图

`pi-arc` 采用与 Pi 一致的语义注释原则，并要求人工编写的文件头、JSDoc/docstring 正文和行内说明统一使用中文；Pi/VISTA 的类型名、API 名、协议字段及其他代码标识符保留英文原名。非平凡生产模块必须用文件头说明职责和边界，导出的类型与 API 必须说明可观察契约，涉及 crash、replay、竞态、持久性、安全或跨运行时一致性的代码必须在最近位置解释“为什么”。这会增加评审与维护成本，但能避免后续 work package 仅复制机制而破坏设计不变量；注释不得复述显然语法，测试只注释非显然的 fault injection 或篡改场景，生成 JSON 的意图由 generator、manifest 和 drift gate 承担。

## 后果

- work package 评审可以拒绝缺少关键语义注释的实现，即使类型检查和测试已通过；评审重点是职责、契约和非显然原因，不是注释数量。
- 评审必须拒绝新增的英文说明性注释；JSDoc 标签、代码标识符、原样错误消息和外部协议文本不视为英文说明性注释。
- 不建立 comment coverage、逐行注释或机械文件 banner 门禁；这类指标会奖励噪声，并不能证明设计意图被保存。
- 行为规范和 ADR 仍是权威决策记录。注释必须与其一致，不得在代码内发明新契约；设计变化应先回到相应文档评审。
